## 1. 共情 Empathize

> ⚠️ 本节全部为待验证假设（基于任务书方向、常识与二手经验推演），尚未经访谈证实。

### 1.1 目标用户是谁

- **主要用户**：在校大学生（本科为主，含低年级与大二以上；覆盖文理工科背景差异）。
- **间接用户**：任课教师（发布任务、提供资料，标准版后才涉及）；班级学习委员/课代表（信息转发节点，先作为场景背景了解，不设专门角色）。
- **用户特征假设**：智能手机重度使用；学习信息来自多个平台；对"又多一个 App/工具"有抵触；对 AI 既好奇又担心答案不可信。

### 1.2 用户在什么时间、地点和场景下使用

⚠️ 待验证假设的场景清单：

| 时间 | 地点 | 场景 |
| --- | --- | --- |
| 每学期开学 | 宿舍 | 把各课程群里的教学大纲、任务清单汇总 |
| 上课前后 | 教室/走廊 | 得知临时通知：调课、作业发布、截止时间提前 |
| 课程群刷屏后 | 宿舍/路上 | 翻聊天记录找"老师第几条消息说的作业要求" |
| 晚间/周末自习 | 图书馆/宿舍 | 决定"今晚学什么"，规划大作业 |
| 考试周 | 图书馆 | 找课程资料、按主题复习、检索老师讲过的概念 |
| 截止前夜 | 任意 | 发现漏了任务，赶工或请求延期 |

### 1.3 用户当前如何完成学习任务

⚠️ 待验证假设：学生在多个渠道间手动同步：

1. 在课程群/通知里看到任务 → 手动记到备忘录/本子/日历/待办 App；
2. 依赖"截图存相册""群聊置顶""文件传输助手"存放资料与要求；
3. 靠同学互相提醒截止时间；
4. 大作业临近才从零开始赶。

### 1.4 用户使用了哪些替代方法或临时解决方法

⚠️ 待验证假设：

- 手机备忘录 / 系统日历 / 待办清单 App；
- Excel 或手写"作业登记表"；
- 课程平台（如学习通/雨课堂/学校教务系统）自带的任务与资料模块；
- 微信收藏、群文件、网盘、U 盘；
- 找学长学姐要往年资料；
- 用通用 AI 聊天工具问问题、帮忙列大纲（但没有课程资料上下文，答案泛化）。

### 1.5 用户遇到的主要困难

⚠️ 待验证假设：

1. **信息分散**：任务分布在教务、课程群、邮件、口头通知多个渠道，难以形成单一可靠视图；
2. **错过截止时间**：群消息被刷走、截止时间在通知中变更、没有统一提醒；
3. **资料难找**：资料按"时间线"散在群里，而非按课程/主题组织；换了电脑/U 盘即丢失；
4. **大任务难启动**：课程设计/论文类大任务缺少拆解方法，倾向于拖到最后；
5. **资料与提问脱节**：想问"老师讲的 XX 概念在课件哪里、怎么理解"时，要先自己翻找资料；
6. **工具切换成本**：已有工具要么不全面（备忘录只管记），要么太重（完整项目管理工具超出学生需要）。

### 1.6 用户可能拒绝使用本系统的原因

⚠️ 待验证假设：

1. "又要多装一个工具/多记一份"，与已有习惯重复；
2. 录入任务与资料需要成本，初期看不到回报；
3. 担心 AI 回答不可信、答错误导复习；
4. 担心隐私：学习数据、资料内容被上传；
5. 界面与交互若不符合学生习惯（尤其移动端）会立刻弃用；
6. 没有同学/老师在用，缺少迁移动力。

### 1.7 学生访谈提纲（可执行版本）

> 设计原则：只问**真实经历**，不诱导答案；不用"你是否需要一个 AI 学习助手"这类暗示题。建议 1 对 1 半结构化访谈，30–45 分钟，先录音（征得同意）后转写。

**A. 学习任务与截止时间**
1. 你最近一次差点或真的错过作业截止时间是什么时候？当时发生了什么，最后是怎么处理的？
2. 你现在一般通过哪些渠道知道"自己有哪些作业、什么时候交"？哪个渠道最可靠？
3. 上周你收到过几次"临时改时间/加任务"的通知？你当时怎么记住的，后来有没有漏？
4. 你用什么记任务（本子/手机/表格/都不记）？为什么用/不用它？

**B. 资料查找**
5. 请回忆最近一次要找一门课以前的课件或资料：你去了哪里找？找了多久？最后找到没有？
6. 你的课程资料一般存在哪几个地方？有没有"明明存过却找不到"的经历？

**C. 大任务与计划**
7. 最近一次比较大的作业（论文/课设）你是什么时候开始动手的？动手前有没有做计划？
8. 如果一个工具能帮大任务拆成每天能做的一小步，你觉得自己会怎么用它？会不会反而觉得烦？

**D. 提问与 AI**
9. 复习时遇到"老师讲过但记不清在哪、什么意思"的内容，你通常怎么解决？
10. 你用过哪些 AI 工具问学习问题？有没有遇到过它答错或答非所问？当时你怎么判断它可不可信？

**E. 收尾**
11. 如果让你设计一个帮你管学习的小工具，你最希望它先解决你上面的哪一件事？为什么？
12. 什么情况下你会用了几天就把它删掉？

> 访谈结束后按第 2 节框架整理：画像、同理心地图、Jobs/Pains/Gains、问题模式，并与 ⚠️ 假设逐条比对，更新本文档状态。

## 2. 定义 Define

> ⚠️ 本节约束条件同上：用户画像与地图内容以假设为主，等 TASK-001 访谈后校准。

### 2.1 用户画像（Persona）

**画像 P1 · 大二学生"小林"（主画像）**

| 维度 | 内容（待验证） |
| --- | --- |
| 基本情况 | 大二，工科，课程量大且分散；有 1–2 门专业课与通识课并行 |
| 学习环境 | 手机随时在线，偶尔用笔记本；学习通/课程群/教务是三大信息来源 |
| 当前行为 | 靠截图+备忘录记任务；资料存在群文件和网盘 |
| 痛点 | 作业漏看、截止时间记混、期末找资料靠翻聊天记录 |
| 目标 | 少漏任务、复习时能快速定位资料并搞懂概念 |
| 技术接受度 | 用过通用 AI 工具，愿意尝试，但对准确性存疑 |
| 拒绝理由 | 怕麻烦：要录入的东西一多就不想用 |

**画像 P2 · 大三学生"阿哲"（次画像，验证任务拆解与统计需求）**：面临课设/论文类大任务，需要拆解与进度感知，习惯用待办 App 但坚持不下来。
**画像 P3 · 教师"王老师"（间接用户，标准版起）**：在课程群发资料与通知，希望学生少问"第几周讲的内容在哪"，但对额外管理成本敏感。

### 2.2 同理心地图（Empathy Map，以 P1 为例）

| 区域 | 内容（待验证假设） |
| --- | --- |
| 说 Says | "这个作业什么时候交来着""谁有第 5 周 PPT""老师上周是不是说改时间了" |
| 想 Thinks | "我又忘了……""任务好多，先玩会再说""这资料到底在哪个群" |
| 做 Does | 截图存相册、群聊@同学确认、截止前赶工、临时抱佛脚找资料 |
| 感受 Feels | 焦虑（怕漏）、拖延后的愧疚、找到资料的如释重负 |

### 2.3 用户任务 Jobs（学生要完成的事）

| 编号 | 任务（Jobs） | 频率 | 重要性 |
| --- | --- | --- | --- |
| J1 | 汇总并跟踪所有课程任务与截止时间 | 持续 | 高 |
| J2 | 在截止前得到可靠提醒 | 每周 | 高 |
| J3 | 按课程/主题找到需要的资料 | 每周–期末集中 | 高 |
| J4 | 理解资料中的概念并回答自己的疑问 | 复习期 | 中高 |
| J5 | 把大作业拆成可执行步骤并跟踪 | 每学期 2–4 次 | 中高 |
| J6 | 了解自己各课程的学习进度与完成情况 | 阶段性 | 中 |

### 2.4 用户痛点 Pains

| 编号 | 痛点 | 关联 Jobs |
| --- | --- | --- |
| P1 | 任务来源分散，容易漏看/记混 | J1 |
| P2 | 没有统一提醒，截止时间变更后无法感知 | J2 |
| P3 | 资料按时间线散落，找不到出处 | J3 |
| P4 | 复习疑问无法快速定位到资料内容 | J4 |
| P5 | 大任务不知从何下手，启动困难、易拖延 | J5 |
| P6 | 缺乏进度感知，不知道自己学得怎么样 | J6 |
| P7 | 录入/管理成本高，工具坚持用不下去 | 全部 |

### 2.5 用户期望收益 Gains

| 编号 | 期望收益 | 关联 |
| --- | --- | --- |
| G1 | 一个地方看全所有任务与截止时间，心里有底 | J1、P1 |
| G2 | 到点提醒、不靠人肉记忆 | J2、P2 |
| G3 | 按课程组织资料，几秒找到 | J3、P3 |
| G4 | 对着自己的资料提问并得到带出处的回答 | J4、P4 |
| G5 | 大任务自动变成"今天做一小步"的清单 | J5、P5 |
| G6 | 能看到完成率与学习趋势，获得正反馈 | J6、P6 |
| G7 | 上手快、录入少、不添乱 | P7 |

### 2.6 反复出现的问题模式

- **模式 A（漏任务）**：任务从"群消息/口头"进入，出口只有一个"人脑记忆"，中间任何一环断了就漏。
- **模式 B（资料时间线化）**：资料以时间顺序（群聊流）而非知识组织（课程/主题）存放，事后检索只能靠翻。
- **模式 C（大任务拖延）**：目标粒度太大（"完成课设"）→ 无下一步 → 拖延 → 截止前集中赶工。
- **模式 D（工具断裂）**：记录（备忘录）与资料（网盘/群）与执行（日历）分属不同工具，没有闭环，任何一处都坚持不住。

### 2.7 核心问题（不预设解决方案）

学生需要一种**更可靠、低成本**的方式，把分散在多个渠道的课程任务、截止时间与课程资料统一起来，并让自己的学习进展（下一步做什么、做到哪了）**随时可见**；同时，当学习疑问产生时，能快速回到**自己的课程资料**找到依据。

### 2.8 POV 问题陈述

> **小林**（一名课程多、信息渠道杂的大二学生）需要**一个可靠且省事的学习任务与资料中枢**，因为他目前靠人脑和截图管理多个渠道的任务，会漏掉截止时间、找不到资料，面对大作业也不知从何开始；
> 我们如何帮助小林**以接近"零额外负担"的方式掌握"要做什么、资料在哪、做到哪一步"**，并在他提问时给出**基于他本人课程资料**的可靠回答？

> 注意：问题定义停留在"需要可靠管理/可见/可检索"层面，不写"需要一个 AI 系统"——AI/RAG 只是实现候选方案之一（见第 3 节）。

## 3. 构思 Ideate

### 3.1 候选方向（7 个）

| 编号 | 方向 | 一句话描述 | 解决的痛点 |
| --- | --- | --- | --- |
| I1 | 任务集中管理 + 截止时间提醒 | 多课程任务一处登记，临近截止自动提醒 | P1、P2 |
| I2 | 课程资料库（按课程组织） | 上传/归类资料，按课程浏览与搜索 | P3 |
| I3 | 基于课程资料的 RAG 问答 | 对资料做向量检索，AI 带出处回答 | P4 |
| I4 | AI 任务智能拆解 / 学习计划生成 | 大任务自动拆成子任务与排期 | P5 |
| I5 | 学习进度统计与可视化 | 完成率、每周投入、课程分布图表 | P6 |
| I6 | 同学间共享学习资料 | 同课学生互传资料、笔记 | P3（社会型解法） |
| I7 | 教师端发布任务/资料 | 教师统一发布，学生自动同步 | P1、P3（源头解法） |

### 3.2 按三个标准筛选

筛选标准：**① 用户是否真正需要；② 当前时间与技术条件是否做得到；③ 是否值得通过原型验证。**

| 方向 | ① 需要性（假设） | ② 可行性 | ③ 值得原型验证 | 结论 |
| --- | --- | --- | --- | --- |
| I1 | 高（P1/P2 是最高频痛点） | 高（纯 CRUD + 时间计算即可） | 高：几乎零风险，是所有功能的地基 | ✅ 保留 |
| I2 | 高（P3 高频） | 高（文件上传 + 列表） | 高：同时是 I3 的前提 | ✅ 保留（与 I3 合并推进） |
| I3 | 中高（P4 在复习期显著） | 中高（文档解析+向量库+LLM，工程量集中） | 高：是"特色技术"与差异化亮点，但风险也最高 | ✅ 保留 |
| I4 | 中高（P5 频次低但痛感强） | 中（LLM 拆解易实现，但"排期合理性"难保证） | 中：值得做小范围验证，可并入基础闭环作为增强 | ✅ 保留（弱化版：建议+可编辑） |
| I5 | 中（P6 为锦上添花） | 高 | 中：依赖任务数据积累，前期数据少 | ⏸ 延后到标准版 |
| I6 | 中（资料共享存在版权与隐私争议） | 中 | 低：课程资料版权边界模糊，本期不做 | ❌ 暂缓 |
| I7 | 高（源头解法） | 中高（需教师侧动因与成本） | 低：教师是间接用户，调研与触达成本高，本期不做 | ❌ 延后（标准版后再评估） |

### 3.3 最终保留方向（3 个）与理由

1. **I1 任务集中管理 + 截止提醒** —— 最贴近"漏任务"核心痛点，纯工程实现、风险最低；它提供后续一切功能的数据地基（任务数据也是统计的数据源）。
2. **I2+I3 课程资料库与基于资料的 RAG 问答** —— 直接回应"资料难找 + 疑问无出处"两大痛点；RAG 是任务书建议的特色技术方向，能形成与普通聊天机器人的本质差异。
3. **I4 AI 任务智能拆解（弱化版）** —— 回应"大任务难启动"；实现上依附于任务模块与 LLM 调用，成本增量可控。为控制范围，第一版只做"生成子任务建议，用户可编辑/重新生成"，不做自动化排期。

> 三个方向彼此互补且共享数据模型（课程 → 任务/资料），合并后即构成"学习任务 + 课程资料 + AI 问答/拆解"的闭环，**不会扩大出孤立的新子系统**。

### 3.4 暂不进入本轮范围的说明

- I5 统计可视化、I6 资料共享、I7 教师发布 → 由标准版及以后承载；其中 I5 因直接消费任务数据，列为标准版第一批。
- Live2D、语音、QQ/Telegram、复杂本地文件操作 → 明确可选，不得影响上述主闭环交付。

## 4. 原型 Prototype（低保真流程说明）

> 目标：说明**页面、用户动作、系统反馈、异常情况**，不追求视觉。六个关键流程如下。所有流程均为待验证设计，等待 TASK-006 原型测试。

### 4.1 流程一：用户登录

- **页面**：登录页（账号+密码 / 注册入口）。
- **动作**：输入学号/账号与密码 → 点击登录。
- **反馈**：成功 → 进入"今日总览"首页；失败 → 页面内提示"账号或密码错误"，不清空账号。
- **异常**：网络失败提示重试；连续失败不锁号（课程场景从简）；未登录访问受保护页面 → 跳转登录页。
- **说明**：注册流程基础版从简（学号+密码+昵称），角色默认学生；教师/管理员账号由 TASK-002/TASK-005 明确注入或管理途径（标准版）。

### 4.2 流程二：创建学习任务

- **页面**：任务列表页（含"新建任务"入口）→ 新建弹窗/表单。
- **动作**：填写任务名、所属课程、截止时间、优先级、备注 → 保存。
- **反馈**：保存后任务出现在列表与"即将截止"区；截止时间当天高亮。
- **异常**：任务名/截止时间为空 → 阻止提交并逐项提示；截止时间早于当前时间 → 提示确认；录入时若该课程尚不存在 → 引导先建课程或在表单内直接创建课程。

### 4.3 流程三：AI 自动拆分学习任务

- **页面**：任务详情页 → "AI 拆分"按钮。
- **动作**：选择一个大任务（如"完成操作系统课设"）→ 点击拆分 → 等待 AI 生成（loading 态，预计 5–20 秒）。
- **反馈**：返回 3–8 条子任务建议（含名称、建议完成日、预估时长），以"待确认"状态展示；用户可逐条编辑、删除、增补，或点击"重新生成"；确认后子任务落入任务列表（主任务标记为已拆分）。
- **异常**：AI 服务不可用/超时 → 明确报错并允许"稍后重试"，不阻断用户手动建任务；子任务日期超出主任务截止时间 → 系统提示并允许用户修正；AI 生成内容为空 → 提示重新生成或手动添加。

### 4.4 流程四：上传课程资料

- **页面**：课程详情页 → 资料区 → "上传"入口。
- **动作**：选择文件（PDF/PPT/DOC/TXT 等）→ 选择目标课程 → 上传。
- **反馈**：上传进度显示；完成后资料出现在该课程资料列表，并可查看"解析状态"（排队中/处理中/可问答/失败）。
- **异常**：格式不支持或超过大小限制 → 明确提示可接受格式与上限；同名文件 → 询问"覆盖/保留两份"；解析失败 → 标记失败原因，允许删除后重传（基础版：解析失败不影响"作为文件存储"功能）。

### 4.5 流程五：根据课程资料提问（RAG 问答）

- **页面**：课程详情页内的"问这门课的资料"对话框，或独立问答页。
- **动作**：选择问答范围（默认当前课程）→ 输入自然语言问题 → 发送。
- **反馈**：返回 AI 回答 + **引用来源列表**（文件名、章节/页码等可定位信息）；无相关内容的回答会明确说"当前资料里没有找到相关内容"。
- **异常**：该课程还没有可问答资料 → 提示先上传并等待解析完成；问题为空/过短 → 提示；检索无结果与 LLM 不可用需区分展示，避免误导用户以为"资料里没有"。

### 4.6 流程六：查看学习进度

- **页面**：统计页（基础版先提供"任务完成情况"简单视图，图表化放入标准版）。
- **动作**：查看各课程任务总数/已完成/逾期；按周查看完成节奏。
- **反馈**：无数据 → 空状态引导（"先去创建第一个任务"）；有数据 → 完成率数字与简单图表。
- **异常**：时间范围非法/为空 → 使用默认范围；数据加载失败 → 重试按钮。

## 5. 测试 Test（原型测试方案）

> 执行载体：`tasks/inbox/TASK-006-prototype-validation.md`。本方案面向低保真原型/可点击原型（可用 Figma 原型、纸面原型或最简前端壳）。

### 5.1 要验证的关键假设

| 编号 | 假设 | 验证方式 |
| --- | --- | --- |
| H1 | 学生愿意把任务集中登记到一个工具（录入成本可接受） | 任务型测试 + 访谈追问 |
| H2 | "即将截止 + 提醒"能减少漏任务（用户确实会依赖它） | 原型任务观察 + 后续可用性访谈 |
| H3 | 按课程组织资料能满足查找需求（替代"翻群聊"） | 任务型测试（找一份指定资料） |
| H4 | 用户信任并采纳"基于自己资料的问答"，会先于通用 AI 使用它 | 提问任务 + 对引用来源的信任度追问 |
| H5 | AI 拆解出的子任务用户愿意采纳/轻编辑，而不是全部推翻 | 拆分任务 + 编辑行为观察 |
| H6 | 主用户（学生）不需要教师功能也能形成价值闭环 | 确认 I7 延后不致命 |

### 5.2 测试对象

- 目标：6–8 名在校大学生，覆盖主画像 P1 与次画像 P2 背景（建议至少 2 名大二以上、1 名有课设/论文经历）。
- 招募：同校同学/朋友，非本项目成员；说明用途并获同意。
- 排除：本项目开发者本人及直接参与文档编写者。

### 5.3 测试任务（按场景，任务化）

1. 你刚收到三条新任务（提供真实感任务卡），请把它们都记进系统，并找到"哪件最紧急"。（覆盖 4.1/4.2）
2. 帮我把"操作系统课设（3 周后截止）"拆成能每天做的小步，然后按你的想法调整。（覆盖 4.3）
3. 上传这份课件到"计算机网络"，然后回答"老师讲的滑动窗口在课件哪里、怎么理解"。（覆盖 4.4/4.5）
4. 现在是周日晚上，告诉我"这周还剩哪些没做完、下周要做什么"。（覆盖 4.6）
5. 收尾访谈：哪些步骤让你觉得麻烦？哪一步让你觉得"这能帮我"？你会在什么情况下卸载它？

### 5.4 观察指标

- **任务完成率**：每个测试任务成功/失败（失败要记录卡点）；
- **用时**：各任务完成耗时（对照无工具基线估计）；
- **求助/出错次数**：需要提示的次数、误操作次数；
- **关键路径偏离**：用户是否按预期流程走，偏离处即设计问题；
- **主观量表**：每任务后 1–5 分"费力度"，收尾 SUS 可用性量表 + 1–10 分"我愿意继续用"；
- **原声摘录**：说"这个有用/好麻烦"的上下文。

### 5.5 可能发现的问题（预判清单，供对照）

| 预判问题 | 可能修正方向 |
| --- | --- |
| 录入任务太繁琐（字段过多） | 收敛字段：名称+课程+截止时间必填，其余可折叠 |
| 用户不知道资料要等"解析完成"才能问答 | 上传后立即给出状态反馈与预期等待时间 |
| 引用来源不够具体（只给文件名） | 检索单元细化到章节/页码级并展示片段 |
| AI 拆解结果与课程安排冲突 | 生成前收集"已知冲突日期"，提供整表编辑 |
| 用户找不到"进度"入口或觉得没意义 | 强化"今日该做什么/本周剩余"入口，弱化报表 |
| 对 RAG 答案信任不足 | 每次回答强制展示来源，无来源时给出明确说明 |
| 只做网页端、移动端体验差 | 原型测试需覆盖手机浏览器；若普遍受阻，调整响应式优先级 |

### 5.6 根据结果如何修改方案

1. 每轮测试后 24 小时内整理问题清单，按"阻断（必须改）/ 重要 / 建议"分级；
2. 阻断级问题直接修改原型与 [02-requirements.md](02-requirements.md) 对应需求与验收标准；
3. 重要问题进入后续迭代列表，标注影响的功能范围与工作量估计；
4. 结论同步更新本文档 ⚠️ 假设状态（已验证/已证伪/待复验），并在 `docs/vibe-log/` 记录；
5. 至少完成两轮（修改后复测），达到"任务完成率 ≥ 80%、无阻断级问题"后方可进入正式系统设计深化（TASK-003 及以后）。
