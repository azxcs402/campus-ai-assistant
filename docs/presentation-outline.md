## 开场 · 0 项目一句话与汇报路线（0.5 min）

- **一句话价值主张**（见附录一）：把分散在课程群/教务/备忘录里的「任务、截止时间、资料」收进一个入口，让 AI 帮忙把大任务变成今天能开始的下一步。
- **汇报路线**：先讲我们如何从用户问题出发（设计思维），再讲系统如何落地（MVP 可运行闭环），以及我们明确没做什么、接下来做什么（RAG）。
- **诚实基调**：一句话点明「当前为可运行的 MVP；用户侧的很多判断仍是待验证假设，已用 ⚠️ 标注」。

**讲法提示**：30 秒内给评委「要解决的问题 + 我们的答案形态」，不要一上来讲技术。
**证据**：[00-project-overview.md](00-project-overview.md) §4 价值主张、§2 项目目标。

## Part A · 设计思维与需求（4–5 min）

### A1 背景与痛点（约 0.7 min）

**要点**：
- 课程要求：从真实用户需求出发，走共情→定义→构思→原型→测试→系统设计全流程（证据：[00](00-project-overview.md) §1、[01](01-design-thinking.md) 引言）。
- 场景假设：大学生学习任务分散在课程群/教务/口头通知；资料按时间线散落；大作业缺拆解；易错过截止时间（⚠️ 全部为假设，尚未访谈）。
- ⚠️ 表达模板：「**我们假设**学生有这几类困扰：漏任务、找不到资料、大作业启动困难……这些将在后续访谈中验证。」

**讲法提示**：讲「现象与场景」而非「我们做了 AI 产品」；主动声明假设属性，是加分项。
**证据**：[01-design-thinking.md](01-design-thinking.md) §1.1–1.6（目标用户、场景、困难清单）。
**图表**：痛点清单卡片 / 时间-场景矩阵（01 §1.2 表格可转图）。

### A2 共情方法与访谈提纲（约 0.8 min）

**要点**：
- 方法：1 对 1 半结构化访谈（30–45 分钟），只问真实经历、不诱导、不用「你是否需要 AI 助手」类暗示题（[01](01-design-thinking.md) §1.7）。
- 提纲五个板块：A 任务与截止 / B 资料查找 / C 大任务与计划 / D 提问与 AI / E 收尾（12 问）。
- **现状说明（重要）**：访谈提纲已就绪，但**尚未开展真实访谈**——执行载体是 `TASK-001-user-research.md`（状态 ready）。不要说「我们访谈了 N 名学生」。

**讲法提示**：把访谈提纲当作「我们为验证假设准备的实验设计」来展示，体现方法论而非结果。
**证据**：[01](01-design-thinking.md) §1.7；[tasks/inbox/TASK-001-user-research.md](../tasks/inbox/TASK-001-user-research.md)。
**图表**：访谈提纲一页清单。

### A3 画像与 POV 问题陈述（约 0.8 min）

**要点**：
- 主画像 P1「小林」（大二、工科、渠道杂、怕录入麻烦）+ 次画像 P2「阿哲」（课设/论文类大任务）；教师 P3 为间接用户（标准版起）——⚠️ 内容均为假设（[01](01-design-thinking.md) §2.1）。
- 同理心地图（Says/Thinks/Does/Feels，以 P1 为例）——⚠️ 假设（§2.2）。

- POV：小林需要一个「可靠且省事的学习任务与资料中枢」——注意问题定义不预设「必须用 AI」（§2.7–2.8）。

**讲法提示**：讲 POV 时强调「问题先于方案」；展示同理心地图能快速让评委共情。

**图表**：同理心地图四象限图（数据取自 01 §2.2）；人物卡 P1。

### A4 构思：7 选 3（约 0.8 min）

**要点**：
- 从 Jobs/Pains 导出 7 个候选方向 I1~I7（任务管理+提醒 / 资料库 / 资料 RAG 问答 / AI 拆解 / 统计 / 共享资料 / 教师发布）。
- 按「用户需要性（假设）× 可行性 × 值得原型验证」三标准筛选：保留 I1、I2+I3、I4（弱化版）；I5 延后标准版、I6/I7 暂缓。
- 三个方向共享数据模型（课程 → 任务/资料），构成「任务管理 + 资料 + AI 问答/拆解」闭环，不扩大出孤立子系统（[01](01-design-thinking.md) §3.3）。

**讲法提示**：展示取舍过程（为什么砍掉教师端/共享资料），比只讲「我们做了三件事」更有说服力。
**证据**：[01](01-design-thinking.md) §3.1–3.4。
**图表**：7 方向矩阵表（01 §3.2）+ 保留 3 方向的闭环示意图。

**证据**：[01](01-design-thinking.md) §4–5；[06-test-plan.md](06-test-plan.md) §5；[tasks/inbox/TASK-006-prototype-validation.md](../tasks/inbox/TASK-006-prototype-validation.md)。

## Part B · 系统与工程实现（4–5 min）

### B1 系统架构（约 0.7 min）

**要点**：
- 三层：Web 前端（原生 HTML/JS，只走 HTTP API，不含密钥）→ 后端应用服务（FastAPI：认证/任务/课程/对话/统计模块 + 统一鉴权与错误处理）→ 存储（SQLite）与 AI 网关（OpenAI 兼容接口，可替换；未配置密钥走演示降级）。
- 数据流：登录鉴权、任务 CRUD 与「即将截止」排序（按服务器时间）、对话消息落库；RAG 管线（资料→切分→向量→检索→带来源回答）在架构中已设计、代码未实现（[03](03-architecture.md) §2/§4）。
- 架构原则：可演示可演进、分层清晰、AI 组件可替换、范围克制（[03](03-architecture.md) §1）。

**讲法提示**：指着架构图讲「数据从哪进、落到哪、AI 在哪一层」，控制在 40 秒内。
**证据**：[03-architecture.md](03-architecture.md) §1–§7。
**图表**：03 §2 总体架构图（重绘为 PPT 版）。

### B2 技术选型（约 0.5 min）

**要点**：

## 收尾 · 范围红线 / 不做什么（约 0.5 min，并入附录二一页）

- **不做什么（范围红线）**：教师发布任务（I7）与同学共享资料（I6）本期不做；Live2D/语音/QQ/Telegram 渠道与复杂本地文件操作明确可选不优先；不做多租户/高并发/生产运维；不做与需求无关的技术依赖（[00](00-project-overview.md) §3.4、[02-requirements.md](02-requirements.md) §5）。
- **收尾一句话**：我们交付的是一个「可运行、可演示、边界清楚」的 MVP 闭环，并把验证过的假设与待验证假设分开标注；下一步按标准版→特色版补齐资料与 RAG，而 RAG 的每一步（切分/索引/检索/溯源）都已写在需求与架构里。
