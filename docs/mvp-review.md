## 3. 用户体验问题清单

> 每条 = 问题现象｜代码证据｜影响｜建议｜优先级｜性质。优先级：**必须修复**＝影响演示可信度/核心流程可理解性，建议在演示前由实现 Agent 处理（需对应 TASK 承接）；**可延后**＝体验优化或依赖更多信息，进后续迭代。

### UX-01 错误提示不一致：字段校验错误显示为「[object Object]」，网络错误为英文
- **问题现象**：部分失败场景用户看到的提示是乱码式 `[object Object]`，另有部分场景完全无提示。
- **代码证据**：`request()` 抛 `new Error(body?.detail || body?.message || '请求失败')`（app.js:11）；FastAPI/Pydantic 默认 422 的 `detail` 是**对象数组**（如注册时账号 <3 位、密码 <6 位），`String(数组)` 得到 `[object Object]`；后端自定义 HTTPException 的 detail 是字符串（中文正常显示）；fetch 网络失败（后端未启动）则抛出浏览器英文「Failed to fetch」，`alert(error.message)`（app.js:31）直接展示英文。
- **影响**：新用户注册/登录遇短账号、短密码（HTML required 拦不住长度，Pydantic `min_length` 生效）时看到不可读报错 → 无法理解错在哪（对照 01 文档 4.1「失败→页面内提示」目标未达成）；后端未启动时整页英文报错，演示开场即穿帮。
- **建议**：前端统一错误解析——`detail` 为数组时取 `detail[0].msg`（并本地化/映射为中文）；网络异常统一转「无法连接服务器，请确认后端已启动」；所有 fetch 调用点补 try/catch 兜底。对接 FR-08/04-api-spec「统一错误结构」的后续实现。
- **优先级**：**必须修复**（演示首屏与新用户注册流程必经）。

### UX-02 截止时间：无格式校验、无时区语义、列表只显示原始字符串、无逾期/临近反馈
- **问题现象**：①后端把 `due_at` 当作任意字符串存取，不做解析与校验；②创建时前端只提交 `YYYY-MM-DD`（无时区），后端 `created_at` 却是 UTC ISO（app.py:38-39），同一任务行混两种时间表达；③任务行展示原始 `截止 ${task.due_at}`（app.js:36），普通用户看不出「还有几天/已逾期」；④无任何临近/逾期视觉反馈，且**逾期任务因排序在未完成区最上方**，可能被误解为「最紧急」。
- **代码证据**：`TaskIn.due_at: str | None` 无 datetime 校验（app.py:167）；前端 `dueAt` 为 `type=date` 提交 `YYYY-MM-DD` 或 null（app.js:45）；renderTasks 直接插值 `task.due_at`（app.js:36）；排序 `ORDER BY … due_at IS NULL, due_at`（app.py:262）；无高亮/剩余时间计算代码。
- **影响**：核心价值 G2/P2（截止感知）在本版本没有兑现载体；若演示脚本用 API 造带时间的 ISO 数据，列表会显示丑陋的 `+00:00` 时间串；用户无法区分任务「是否要到期/是否已过期」（推断，需测试验证其对原始日期的理解力）。对照 AC-09-2/AC-09-3 与 01 文档 4.2「截止当天高亮」。
- **建议**：后端将 due_at 解析归一化为统一口径（接受 `YYYY-MM-DD` 与 ISO，统一按服务器时区解释）；对「早于当前时间」给出明确 400（04-api-spec 3.2 已给出该错误示例）；前端渲染「今天截止/已逾期 N 天/还有 N 天」相对文案并高亮 24h 内任务，与 FR-09 一起实现。
- **优先级**：**必须修复**（任务的时间性是需求第一痛点 P2 的载体；演示若展示带日期任务而无任何语义反馈，价值主张说不通）。性质：问题①②为代码事实，③④对用户理解力的影响为推断。

### UX-03 AI 状态标识硬编码为「演示模式可用」，与真实状态脱节；等待与失败无区分
- **问题现象**：①AI 面板徽标**永远显示**「演示模式可用」+ 绿点（index.html:33、styles.css:13 绿点语义），即使后端配了真实 LLM_API_KEY 也照旧；②发送后无 loading/「思考中」态，最长可静默等待后端 25 秒（app.py:342 timeout=25）；③后端三种文本——真实回复、演示文本（app.py:323）、错误文本（app.py:346）——都以 200 落库并渲染成同一样式的 assistant 气泡，用户无法区分「这是 AI 真话/占位/故障」，错误时也无重试按钮。
- **代码证据**：硬编码徽标在 index.html:33；前端无法获知 AI 模式（无 /auth/me 扩展或配置接口）；chatForm submit 立即清空输入框并乐观插入气泡后 await（app.js:47），无 pending 状态变量、无 disabled；后端错误文案作为正常 assistant 消息返回并持久化（app.py:358）。
- **影响**：用户对 AI 的信任是本项目设计中的关键张力（01 文档 P1「对准确性存疑」、拒绝理由 3）；徽标误导会放大不信任（配了真模型却说演示模式，用户以为系统在敷衍；没配模型时绿点又暗示一切正常）。对照 NFR-02「超时给出明确提示」、AC-06-3「可读错误并支持重试」。
- **建议**：由后端暴露 AI 配置态（如 /auth/me 增加 ai_mode: real/demo/error），前端动态渲染徽标文案与颜色；发送消息期间禁用输入并显示「AI 正在思考…」；把「错误/演示占位」与真实回复区分样式，并提供「重试」按钮。对用户体验损害的程度为推断，待测试验证。
- **优先级**：**必须修复**（现场演示大概率会演示 AI 对话，状态标识错误会直接误导观众与用户）。

### UX-04 会话历史不可见、不可切换、不可新建，前端永远复用第一个会话
- **问题现象**：刷新页面后对话「看起来还在」（历史消息被重新渲染），但用户：①看不到会话列表，无法区分/管理多段对话；②没有任何「新对话」入口；③所有新消息总是追加到 `conversations[0]`（最新更新的那个）。
- **代码证据**：`if (conversations.length) conversationId = conversations[0].id; else conversationId = (await request('/conversations', …)).id`（app.js:29）；只有 loadData 时创建一次会话；index.html 无会话列表 DOM；后端会话列表/消息读取能力已具备（app.py:314-369）但前端未消费。
- **影响**：FR-07 AC-07-3「打开历史会话能加载完整消息序列并继续对话」在界面层不成立；且由于后端多轮上下文尚未接入（UX-03 相关），用户会觉得「AI 每次都像失忆」（推断）。对「多轮/多主题提问」场景（01 文档 4.5、Jobs J4）是硬缺口。
- **建议**（二选一或都做）：短期内最省力的方案是把前端限制如实写进演示口径；正式建议补「会话侧栏/新建按钮 + 切换时 GET messages」，并让 send_message 携带历史（服务端组装最近 N 轮）。属 FR-07/FR-06 的补全，需承接 TASK。
- **优先级**：**必须修复**（对话记录保存是任务书门槛⑤，界面层不可达则演示价值减半）；若时间不允许，至少应把「当前只能一个会话」做成可理解的界面约束而非静默行为。

### UX-05 提交无防重复、多处失败路径静默（任务创建/完成/删除/发送均无 try/catch）
- **问题现象**：①双击「添加任务」会重复 POST 创建两条相同任务；双击「发送」会重复发消息；②任务创建失败（如网络断/不是课程成员 403）时**没有任何提示**，表单也不 reset，用户以为成功了却没看到任务；③聊天发送失败时，界面已乐观插入用户气泡、输入框已清空，但消息未落库且无报错 → **用户的话「凭空消失」**。
- **代码证据**：taskForm/chatForm/完成/删除/注册 handler 均无 try/catch（app.js:37-47）；按钮无 disabled/防抖（对照 AC-08-5、06-test-plan ET-06）；乐观插入在 await 之前（app.js:47）。
- **影响**：数据重复与「自以为已保存」是待办类工具最伤信任的错误（01 文档拒绝理由 1/2 关联的录入成本与可靠感知）；完成/删除静默失败会让用户对列表状态产生错误认知（推断，需测试验证用户是否注意到列表没变化）。
- **建议**：提交期间禁用按钮 + 所有异步 handler 统一 try/catch 并给出 toast/内联错误；聊天失败恢复输入框内容；后端对任务创建加幂等键或前端防抖即可满足 ET-06 精神。删除按钮可保留 confirm（AC-02-3 已满足）。
- **优先级**：**必须修复**（数据可靠性类问题，直接影响演示可重复操作时的观感）。

### UX-06 首次登录静默自动创建默认课程，用户对「我的课程」无掌控感
- **问题现象**：新注册用户登录后，系统自动创建一门名为「系统设计与实践 / 2026 秋」的课程，全程无任何提示；用户看到任务表单里已预选了一门自己没建过的课，可能困惑「这门课哪来的？我能删吗？」（删除入口不存在）。
- **代码证据**：`if (!courses.length) await request('/courses', { method: 'POST', body: JSON.stringify({ name: '系统设计与实践', semester: '2026 秋' }) })`（app.js:25）；无课程管理视图（对照 FR-03 AC-03-2/AC-03-3）。
- **影响**：自动建课对演示「开箱即用」有好处，但静默副作用违反 01 文档 4.2「该课程不存在→引导先建课程/表单内创建」的引导原则；用户无法改名/删除默认课程，会把后续所有任务的归属误解为系统强制（推断）。
- **建议**：建默认课程时给出可见 toast（「已为你创建默认课程 X，可在课程下拉中新增课程」）；或改为引导式「先创建第一门课」空状态；补课程管理的最小 UI（列表/新增/删除确认）。删除课程须处理级联（AC-03-3 二选一并写明）。
- **优先级**：**必须修复**（首登 30 秒内的困惑最伤留存）；最小修复（一行 toast/提示文案）成本极低。

### UX-07 登出无确认、令牌无失效机制（安全边界说明类问题）
- **问题现象**：点击「退出」立即登出，无确认；登出只清 localStorage，后端无 `/auth/logout`，token 也**无过期时间**（签名 = `user_id + HMAC`，app.py:120-123），拿到 token 的人可永久使用。
- **代码证据**：logout 仅 `localStorage.removeItem + location.reload()`（app.js:18）；无 /auth/logout 路由；TOKEN_SECRET 默认 `dev-only-change-me`（app.py:25）；token 不带时间戳。
- **影响**：误点退出需重登（影响小）；token 永久有效 + 默认弱密钥在课程演示环境风险有限，但作为「可退出登录」的完整语义（FR-01 AC-01-4、04 草案 logout 接口）不达标；属安全/健壮性项，非当前主流程阻断。
- **建议**：登出加 confirm 或改为后端注销+前端清理；token 增加签发时间与过期校验（≥演示时长即可）；演示环境提醒更换 TOKEN_SECRET。此项与前几项比优先级低。
- **优先级**：**可延后**（可在演示前仅处理「登出确认」一个交互点，令牌机制随标准版 FR-11/FR-08 一并做）。

### UX-08 空状态与引导不足：聊天区空白无引导，任务/统计空态文案简单
- **问题现象**：首登后 AI 对话区是全空白（聊天记录区高度 350px+ 空框），用户不知道可以问什么、也看不到「演示模式」说明；任务空态只有一句「还没有任务…」；统计卡全 0 无解释。
- **代码证据**：index.html:33 chat-log 无初始占位内容；`renderChat` 只在有消息时填充（app.js:40）；演示模式回复里「你也可以先把它整理为一个学习任务」是唯一引导性文案，且无对应按钮（app.py:323）。
- **影响**：对照 06-test-plan ET-08「空状态引导而非报错/白屏」精神未完全落地；无引导的空聊天框会让新用户不知所措（推断，01 文档 5.5 预判的「录入成本/不知道能干嘛」风险点）。
- **建议**：聊天区放示例提问 chips（如「帮我规划一周复习」「今天该做什么」）与模式说明条；任务空态给「添加第一个任务」的聚焦动作；统计空态说明「完成一个任务后这里会变化」。成本低，收益在演示首屏。
- **优先级**：**可延后**（不阻断主流程；演示前若只做一个，优先 UX-01/UX-05 类正确性问题）。

### UX-09 任务「编辑」入口缺失：改截止时间/标题/优先级需删除重建；备注字段不可录入
- **问题现象**：任务创建后只能「完成/恢复/删除」；想改截止时间（演示中高频操作，如模拟「老师改时间」场景，01 文档 1.2/2.6 模式 A/B）必须删了重建；表单也没有备注字段。
- **代码证据**：taskList 的 action 只有完成/恢复与删除（app.js:36-38）；新建表单字段 title/course/dueAt/priority（app.js:45）无 note；后端 PATCH 支持 title/due_at/priority/note/status（app.py:172-177）但无 UI 使用。
- **影响**：FR-02 AC-02-2 不达标；「截止时间变更无法感知」（P2 的核心痛点场景）在演示中无法自然演绎。
- **建议**：给每条任务加「编辑」→ 弹窗/行内表单（标题/截止/优先级/备注/状态）；成本可控且直接补上 AC-02-2。
- **优先级**：**必须修复**（FR-02 是任务书门槛②，「增删改查」的「改」在界面层缺失）；如时间紧张可与 UX-02 的日期语义一起做。

### UX-10 移动端与输入法适配未验证，日期控件与响应式行为属假设风险
- **问题现象**：styles.css 有 800px/520px 两档媒体查询（styles.css:14-15），但从未在任何真机/手机浏览器上验证；`type=date` 在移动端弹出的日历交互、任务表单 2 列网格下长文案输入、聊天键盘弹起遮挡均无实测。
- **代码证据**：仅能静态确认存在响应式断点与 viewport meta（index.html:5）；NFR-06「移动端浏览器可用」无测试记录。
- **影响**：01 文档 5.5 预判清单已把「只做网页端、移动端体验差」列为已知风险；主要用户画像 P1「手机随时在线」（01 文档 2.1），若课堂演示只用桌面浏览器则风险被掩盖。
- **建议**：在 demo-user-test 中加一项「手机浏览器打开同一 URL 完成添加任务+提问」的观察（见 demo-user-test 场景 S6）；结论出来前不宣称已适配移动端。
- **优先级**：**可延后**（依赖测试证据；作为待验证项进入用户测试）。

### 4.1 覆盖情况（代码事实 ↔ 01 文档 Jobs/Pains/Gains 映射）

### 4.2 推论（推断，需用户测试验证）

1. **MVP 最小闭环价值主张 = 「登录 → 建任务 → 完成 → 简单统计 → 可对话」**。它对 P1（集中登记）与 P6（进度感知）提供最弱可用的载体，但 P2（截止感知）在界面层不可感。现场演示若主打「解决漏截止」，需要 FR-09/UX-02 补位或调整演示故事线。
2. AI 对话当前只是「附加演示点」而非「基于资料的可信助手」——演示口径上它是普通文本对话（FR-06），**不能**表述为「基于你的课程资料回答」（RAG 未实现）。
3. 哪些 UX 判断属于假设、必须经用户测试：用户是否困惑于自动建课（UX-06）、是否能读懂原始日期串与列表次序（UX-02③④）、是否期待多会话管理（UX-04）、对无 loading 的长等待是否流失（UX-03）、移动端是否可用（UX-10）——均已标注【推断】，验证方法见 [demo-user-test.md](demo-user-test.md)。

## 5. 结论与优先级汇总

### 5.1 必须修复（演示前建议处理，按演示影响力排序）

| 编号 | 问题 | 一句话理由 |
| --- | --- | --- |
| UX-01 | 错误提示 `[object Object]`/英文/部分静默 | 首屏与注册流程即可见，最伤信任 |
| UX-02 | 截止时间无校验/无相对语义/无临近反馈 | 需求第一痛点 P2 的价值载体缺失 |
| UX-03 | AI 徽标硬编码「演示模式可用」+ 无等待/失败区分 | 现场演示 AI 环节会直接误导 |
| UX-04 | 会话历史界面层不可见/不可切换 | 任务书门槛⑤「记录保存」的界面层不成立 |
| UX-05 | 双击重复提交 + 静默失败路径 | 数据重复/“以为存了”最伤待办工具信任 |
| UX-06 | 默认课程静默创建、无课程管理入口 | 首登 30 秒困惑点，最小修复成本极低 |
| UX-09 | 任务无编辑入口（缺「改」） | FR-02「增删改查」门槛缺一环 |
| R-1 | FR-04 课程资料列表未实现 | 门槛③不达标，**需人工决策**（补最小实现或修订 02/00 文档范围） |
